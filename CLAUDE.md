# Daily Game Challenge backend

## Project state

Dependency management runs on uv: direct dependencies are in `pyproject.toml` (runtime under `[project]`, test and lint tools under the `dev` group, and under the `content` group the libraries only the content scripts need; `httpx` is in both groups, because the tests need it) and every version, direct or transitive, is pinned in `uv.lock`. Core infra (`app/core/config.py` Settings, `app/core/db.py` async engine/session, Alembic under `app/alembic/`) is wired up. The only domain so far is `app/auth/`: register, login, logout and the current user via Redis-backed sessions (`POST /v1/auth/register`, `POST /v1/auth/login`, `POST /v1/auth/logout`, `GET /v1/auth/me`), plus forgot, reset and update password (`POST /v1/auth/forgot-password`, `POST /v1/auth/reset-password`, `POST /v1/auth/update-password`). The game data model exists (M1-10a: `games`, `titles`, `puzzles`, `puzzle_clues`, `clue_media_files`), and the first game routes do too (M1-10): the game list, today's puzzle and a puzzle by date. `GET /v1/clock` (M1-17) returns the server's time. The title search (M1-11) is `GET /v1/games/{slug}/titles?q=`. The guess route (M1-12) is `POST /v1/games/{slug}/puzzles/{date}/guesses`. Account progress (M1-13) is stored by it, and `POST /v1/games/{slug}/puzzles/{date}/resume` shows a game again after a reload. Clue media with signed links and byte ranges (M1-18) is `GET` and `HEAD /v1/media/{key}`. Stats and the streak (M1-14) are `GET /v1/games/{slug}/stats`. The archive (M1-16) is `GET /v1/games/{slug}/archive`. The guest merge (M1-15) is `POST /v1/games/{slug}/progress/merge`. That completes the Phase 1 backend routes (see "What this is"). The suite lives in `tests/`. `tests/conftest.py` provides session-scoped `engine` (auto-creates `TEST_DATABASE_URL`'s database, creates/drops all tables), function-scoped `db_session` (one transaction per test, rolled back after via a savepoint-joined `AsyncSession`, so `service`-layer `commit()` calls don't leak between tests), and `client` (httpx `ASGITransport` client with `get_db` overridden to `db_session`). `asyncio_default_fixture_loop_scope`/`asyncio_default_test_loop_scope` are pinned to `session` in `pyproject.toml` so the session-scoped engine and per-test event loops don't end up on different asyncio loops (a real asyncpg failure mode otherwise). `engine` also runs `CREATE EXTENSION IF NOT EXISTS pg_trgm` before `create_all`, because the tests build tables without migrations and the title indexes need the extension. `TEST_DATABASE_URL` defaults to `localhost:5433/daily_game_challenge_test`, the same host and port as the dev database with a `_test` suffix.

`redis` is installed and used for auth sessions and password reset tokens (`app/core/redis.py`). `arq` is **not installed**. It is planned for real email sending (M1-43); add it when that work starts. Until then `app/core/email.py` is a stub that logs the reset link in `local` and `test` only.

Errors, health and config (2026-10-27): every error body follows the contract in `../CONTRACTS.md` ("Errors"): raise an `AppException` subclass with a `code` (`app/core/exceptions.py`), never an English-only `detail`; handlers live in `app/core/errors.py` and every response carries `X-Request-ID`. `GET /healthz` and `GET /readyz` exist (`app/api/health.py`). `ENVIRONMENT` is `local`, `test`, `staging` or `production`; every environment refuses to start when `FRONTEND_URL` is not an absolute http(s) URL, and `local` and `test` also when `API_BASE_URL` or any `BACKEND_CORS_ORIGINS` entry is not (they feed the allowed origins there only); `staging` and `production` additionally refuse a placeholder `SECRET_KEY`, a non-https `FRONTEND_URL` or localhost CORS origins (`app/core/config.py`). Passwords use argon2id (`app/core/security.py`, async wrappers). The test suite points the app at `TEST_DATABASE_URL` and `TEST_REDIS_URL` (it drops tables and flushes that Redis database, so both must differ from the dev ones). CI is `.github/workflows/ci.yml` (lint, test, migrations, openapi). The API is mounted under `/v1`; `openapi/openapi.json` is the contract snapshot the frontend generates its types from: after changing any route or schema run `uv run python scripts/export_openapi.py` and commit it (a test and CI fail otherwise); a breaking change needs the `breaking-change` pull request label.

## Commands

Install uv (https://docs.astral.sh/uv/), then set up the venv (Python 3.12, from `.python-version`; uv downloads it if the system has another):
```
uv sync            # creates .venv and installs exactly what uv.lock says (runtime + the default groups dev and content)
uv sync --no-default-groups   # runtime only: no dev, no content (no httpx)
```

Run the dev server (auto-reload):
```
uv run uvicorn app.main:app --reload
```

The app serves on `http://127.0.0.1:8000` by default. In dev, reach it via `http://localhost:8000` (not `127.0.0.1:8000`) from the frontend — the session cookie is host-scoped, and `127.0.0.1`/`localhost` are different hosts for cookie purposes, so a cookie set via `127.0.0.1` won't round-trip to a `localhost:5173` origin. `localhost` already resolves to `127.0.0.1`, so no bind-host change is needed, just consistent hostnames on both sides.

Other common commands:
```
uv add <pkg>                                   # add a runtime dependency (uv add --dev <pkg> for tools); updates pyproject.toml and uv.lock
uv lock --upgrade-package <pkg>                # upgrade one package in uv.lock
uv run ruff check .                            # lint
uv run ruff format .                           # format (CI runs ruff format --check .)
uv run pytest                                  # run tests (needs Postgres and Redis, see below)
uv run python scripts/export_openapi.py        # rewrite openapi/openapi.json (add --check to only compare)
uv run alembic revision --autogenerate -m "message"   # new migration
uv run alembic upgrade head                    # apply migrations
```

Commit `uv.lock` with every dependency change; CI runs `uv sync --locked` and fails when the lock is stale.

Copy `.env.example` to `.env` and adjust values before running anything that touches the DB (`DATABASE_URL` points at Postgres).

`docker compose up -d` starts Postgres 16 (host port 5433, database `daily_game_challenge`) and Redis 7 (port 6379).

Old local database: the database used to be called `item_list`. A volume `my-list-be_db_data` created before the rename still holds only that old database, because the Postgres image applies `POSTGRES_DB` only to an empty data folder. Local data is test data and is not migrated. To start clean: `docker compose down`, `docker volume rm my-list-be_db_data`, `docker compose up -d`, `uv run alembic upgrade head`. Then copy the new `DATABASE_URL` and `TEST_DATABASE_URL` from `.env.example` into your `.env`. The test suite creates the test database itself.

## What this is
The FastAPI backend of Daily Game Challenge, a site with daily puzzle games (product spec: `../SPEC.md`, plan: `../MILESTONE-1.md`). Today it has accounts (auth and password flows), the health checks, the error contract and the OpenAPI snapshot. The game tables, the puzzle visibility rule, the clock dependency, the game list and the puzzle view are in place; the title search is in too (M1-11), and so are the guess (M1-12), the account progress with resume (M1-13), the clue media (M1-18), the stats route (M1-14) the archive (M1-16) and the guest merge (M1-15).

This is a learning/practice project built deliberately with production-grade patterns — the goal is real-world architecture, not shortcuts.

## This repo
FastAPI backend only. The frontend is the sibling repo `../my-list-fe`, a Vite/React SPA running at `http://localhost:5173` in dev.

## Stack
- FastAPI, Python 3.12, managed with **uv** (`pyproject.toml` + `uv.lock`, `.venv` created by `uv sync`)
- SQLAlchemy 2.0 **async** + asyncpg, PostgreSQL 16
- Alembic (async template) for migrations
- Redis 7 for sessions and password reset tokens
- argon2id password hashing (`argon2-cffi`)
- Session-based auth: opaque server-side session token in an httpOnly cookie, session store is Redis (no Postgres sessions table, no JWT)
- boto3 (M1-18) for presigned links to an S3-compatible bucket (Hetzner Object Storage); planned, not installed: arq for background jobs (email sending, M1-43)

## Architecture
Layered structure under `app/`: router, service, query layer, models. Dependencies point one way: a router calls a service, a service calls the query layer in `app/crud/`, the query layer uses the models in `app/models/`. Today's layout:
- `app/auth/`: the auth domain (`router.py`, `schemas.py`, `service.py`).
- `app/crud/`: the query layer, one file per entity (`app/crud/<entity>.py`). `user.py`, `game.py`, `title.py`, `puzzle.py`, `clue_media.py` and `progress.py` for the database, `session.py` for Redis sessions, `password_reset.py` for Redis reset tokens.
- `app/models/`: SQLAlchemy models (`User`; `Game`; `Title`; `Puzzle`, `PuzzleClue` and `ClueMediaFile`; `Progress` and `ProgressGuess`; `AnswerExclusion`).
- `app/clock/`: `GET /v1/clock` (`now`, `today`, `next_reset`, `Cache-Control: no-store`), built only from the clock dependency: no session, no database. The client uses it for display only; "today" for every game rule is decided on the server.
- `app/games/`: the game domain. `router.py` (tag `games`, mounted at `/v1/games`), `schemas.py`, `service.py`, `enums.py` (`ProgressStatus`, `ArchiveState`, `GuessResult`, and the clue media enums `MediaType`, `ClueRole`, `ClueContentType`, which the models import), `normalize.py` (the one normalizer for title names and franchises), `stats.py` (the stats and streak rules, pure) and `modules/`: the game modules, one per game, registered by slug in `modules/__init__.py` (a game row with no module answers `game_not_found` and is logged at debug level).
- `app/media/`: clue media. `signing.py` (the HMAC link signature, the media key shape), `storage.py` (`LocalMediaStorage` and `S3MediaStorage`, both with `signed_url(key, content_type, now)`, and the `get_media_storage` dependency), `ranges.py` (reading `Range`), `service.py` (checks a link and finds its file) and `router.py` (the local route).
- `app/api/`: `deps.py` (dependencies such as the current user, and `OptionalUser`, which is `None` for a guest; `MediaStorageDep`), `health.py` (`/healthz`, `/readyz`), `main.py` (the `/v1` router that aggregates the domain routers).
- `app/core/`: cross-cutting code, namely config, DB engine and session, Redis client, security, exceptions and error handlers, logging, request id, OpenAPI helpers, health checks, the email stub.
- `app/alembic/`: migrations.
- `app/main.py` creates the `FastAPI()` instance, mounts the health router at the root and the API router under `/v1`.

The game domains (Phase 1) follow the same layering. Game code goes in `app/games/` (router, schemas, service, game modules), its queries in `app/crud/<entity>.py` (not in `app/games/`, because puzzles, titles and progress are read by many routes), its tables in `app/models/`.

Database conventions:
- `Base.metadata` has a constraint naming convention (`app/core/db.py`): `ix_`, `uq_`, `ck_`, `fk_` and `pk_` names built from the table and column. Give every `CheckConstraint` a `name=` (the table name is added: `name="status"` becomes `ck_puzzles_status`). The `users` primary key was renamed to `pk_users` in the first game migration, so a migrated database and the one `create_all` builds in tests have the same names.
- A CHECK built from a StrEnum (`enum_check` in `app/core/db.py`: statuses, kinds, media types, clue roles and content types) is stored as text in the database. Changing the enum needs a hand-written migration that drops and re-creates the CHECK, because `alembic check` does not compare CHECK text.
- `Base` sets `__mapper_args__ = {"eager_defaults": True}`, so `updated_at` can be read after a flush with no lazy load (AsyncSession cannot lazy-load). A model that defines its own `__mapper_args__` must keep `"eager_defaults": True`.
- Tables of the game domain have plural names and integer keys; `users` keeps its UUID.
- Puzzle visibility is one SQL condition, `visible_puzzle_condition(today)` in `app/crud/puzzle.py` (scheduled, date today or earlier, on or after the game's launch date, game enabled). Every puzzle query takes it; do not write a second copy.
- Time comes from `app/core/clock.py`: `get_now` (UTC, timezone aware) is a FastAPI dependency (`NowDep`) that tests override, `utc_today(now)` gives the UTC date, `next_utc_midnight(now)` the next 00:00 UTC (strictly after `now`). Services take `now` as a parameter.
- `titles.normalized_name` and `titles.normalized_franchise` have GIN indexes with `gin_trgm_ops` (`ix_titles_normalized_name_trgm`, `ix_titles_normalized_franchise_trgm`), created by the migration that also runs `CREATE EXTENSION IF NOT EXISTS pg_trgm` (a trusted extension, so a database owner can create it). `alembic check` does not compare operator classes: after editing such a migration, compare a database built by `alembic upgrade head` with one built by `create_all` (`pg_indexes`, `pg_get_constraintdef`).
- `normalized_name` and `normalized_franchise` are written only by `create_title` and `update_title` in `app/crud/title.py`, through `normalize_text`.
- Content columns (M1-22a, SPEC-04; the one Phase 3 migration, `fddebd9d28de`). `puzzles.date` is optional: only a scheduled puzzle must have one (`ck_puzzles_scheduled_has_date`), and the content tools write `NULL` for a puzzle that is not scheduled. The unique key `(game_id, variant, date)` still holds, because Postgres treats NULLs as distinct. `puzzles.build_slot` (positive, unique per game and variant), `generator_version` and `approved_at` are the builder's records; `puzzle_clues.source_image_ids` holds the IGDB image ids a clue was made from and is never in a response; `titles.igdb_id` is nullable and unique. `answer_exclusions` (`app/models/exclusion.py`, reason `rebuild` or `never` from `ExclusionReason`) holds the titles a reviewer held back as an answer, per game and variant (`rebuild` needs a `build_slot`, `never` has none). A visible puzzle always has a date, and `_puzzle_data` in `app/games/service.py` raises `PuzzleDataError` if it has none. The downgrade drops the Phase 3 table and columns with their data and refuses, before changing anything (also with `--sql`), while a puzzle has no date.
- Test helpers that build games, titles and puzzles with six clues are in `tests/factories.py`.

Game domain (M1-10):
- Routes: `GET /v1/games` (enabled games that have a module, `public, max-age=300`), `GET /v1/games/{slug}/puzzles/today` and `GET /v1/games/{slug}/puzzles/{date}` (`private, no-store`). Both puzzle routes take an optional `variant` (default: the game's default variant, named `default`). Declare `today` before the dated route, or it is read as a date and fails with 422.
- A game module (`app/games/modules/base.py`) works on plain dataclasses and does no I/O, so a guest's replay and an account's stored state can run the same code. It has `max_guesses`, `has_variant`, `get_puzzle` and `submit_guess`. `get_puzzle` builds the view from the puzzle, the progress state, whether the caller is signed in and `sign`, a function the service passes in that makes the signed link of a file (the module never sees storage); it shows steps 1 to `guesses_used + 1` while the game runs and all six, with `source_url` and the answer, at the end. A scheduled puzzle that does not have exactly the steps 1 to 6, or whose media break the AC-13b rules (an image clue has one `image/webp` file and no poster; a video clue has one `video/mp4`, at most one `video/webm` and one poster), raises `PuzzleDataError` (`app/core/exceptions.py`), which is a 500 `internal_error`: the response says nothing about the cause, and the handler logs the reason.
- The service checks in this order: the game (enabled, with a module; else `game_not_found`), the variant (else `variant_not_found`), then the visible puzzle (else `puzzle_not_found`). The puzzle is loaded with its answer title and its clues in one query (`get_visible_puzzle_with_details`; the `Puzzle` relationships are `lazy="raise"`, so any other access fails loudly instead of lazy-loading). Every hidden puzzle (draft, not scheduled, future date, before launch) raises the same `PuzzleNotFoundError` with the same detail, so the 404 bodies differ only in `request_id`.
- `OptionalUser`: a missing, unknown or expired cookie, or an inactive user, is a guest and the view says `signed_in: false`. Game routes never answer 401, except stats and merge, which need an account.
- Path and query dates use `StrictDate` (`app/games/schemas.py`): exactly `YYYY-MM-DD` and a real day, else 422 `validation_error` with `field: "date"`. Validation errors name the bare field: the first part of `loc` (`body`, `path` or `query`) is dropped, a later part with the same name is kept (`field_from_location` in `app/core/errors.py`).
- The view number is days since the game's launch date plus 1. A guest's view has an empty progress state, so `counts_for_streak` is `null`; an account's view is built from its stored game (see "Account progress").

Guess (M1-12): `POST /v1/games/{slug}/puzzles/{date}/guesses` (`games_submit_guess`, `private, no-store`) takes `{title_id: int | null, previous: [int | null]}` (both required; `null` is a skip; `previous` capped at 20 entries by the schema, a size guard that gives `validation_error`) and returns the new view. A guest's guess stores nothing (AC-37); an account's guess is stored (see "Account progress").
- The rules are in `GameGuesserModule.submit_guess` (pure, `app/games/modules/game_guesser.py`): correct when the title is the answer or has the same normalized name; `franchise` when wrong and both normalized franchises are present and equal (a missing franchise never matches); a skip is `skipped`; the sixth guess or skip that is not correct loses; the score is `guesses_used`. It raises its own errors (`TitleAlreadyGuessedError`, `TitleKindMismatchError`, `GameFinishedError`, in `modules/base.py`, checked in the order finished, kind, duplicate) and changes nothing; the service maps them to the API's codes. `TitleData` has a `kind` and `PuzzleData` a `title_kind` for the kind check.
- `submit_guess` in `app/games/service.py` (the guest flow, `_submit_guest_guess`; the replay is `_replay_previous`, shared with resume), in this order: the game, the variant and the visible puzzle (the same `_load_puzzle` as the view); `previous` with `max_guesses` or more entries gives 422 `invalid_guess_history` (AC-39: over 5 on a guess); one query loads every title of `previous` and the new one (`get_titles_by_ids` in `app/crud/title.py`, which leaves out ids of another kind and ids too large for a 32-bit key, so they are "not found" and never a 500); `previous` is replayed through the module, and an unknown title, a duplicate or an entry after the end is `invalid_guess_history`; a replay that ended the game gives 409 `puzzle_already_finished` (before the new title is looked at); an unknown title or one of another kind is 422 `title_not_found`; a title already in `previous` is 422 `duplicate_guess`. A title counts as already guessed when its id or its normalized name equals that of an earlier guess (the same equivalence as a correct guess, Q9: "Portal 2" and "PORTAL  2" are one guess), so a `previous` with such a pair is `invalid_guess_history`. `counts_for_streak` is "today equals the puzzle's date" when `previous` is empty (so a 23:59:59 view guessed at 00:00:01 is `false`) and `null` otherwise (AC-40).
- Validation codes (`app/core/errors.py`): pydantic's `int_type`, `list_type` and `model_attributes_type` (a body that is not an object) give `invalid_type`, and a list over its `max_length` gives `too_long` with `params: {"max": N}`, like a string. A number under its `ge` gives `too_small` with `params: {"min": N}` and over its `le` gives `too_large` with `params: {"max": N}`; `int_parsing` and `int_parsing_size` (over 4300 digits) give `invalid_type`. The bounds go through `jsonable_encoder`, so a date or Decimal bound cannot turn the 422 into a 500, and a non-finite bound (`inf`, `nan`) is left out of `params`. `gt` and `lt` are not mapped (no route uses them). The module's franchise rule needs both normalized franchises to be non-empty, so an empty string never matches. The service maps the module's `TitleKindMismatchError` to `title_not_found` (the SQL kind filter normally stops a foreign title first).
- Exceptions: `TitleNotFoundError`, `DuplicateGuessError`, `InvalidGuessHistoryError` (422) and `PuzzleAlreadyFinishedError` (409) in `app/core/exceptions.py`.
- Tests: the rules are tables in `tests/test_game_guesser.py` (no database); `tests/test_guesses.py` has the replay table, the `counts_for_streak` table, the leak scan over a won and a lost game through the route (the one route happy path), and the request validation table. `set_now` (fix the server clock; it removes its override at teardown) is in `tests/conftest.py`.

Account progress and resume (M1-13). `submit_guess` and `resume_puzzle` in `app/games/service.py` take the signed-in user from `OptionalUser`; with a user they run the account flow, without one the guest flow above.
- Tables (`app/models/progress.py`): `progress` (one row per `(user_id, puzzle_id)`, deleted with the user; `status`, `started_at`, `finished_at`, `counts_for_streak`, `is_test`, `origin` `play` or `merge`) and `progress_guesses` (`progress_id`, `position`, `title_id`, null for a skip). The puzzle foreign key is `RESTRICT`, so a stored game keeps its puzzle. A guess row's title foreign key is `RESTRICT` too (AC-11), unique on `(progress_id, position)` and, for non-null titles, on `(progress_id, title_id)`. The stored guesses hold no result column: the state is rebuilt by running them through the module's `submit_guess` (`_state_from_progress`), the same code a guest's replay uses, so the views agree (AC-44). A stored game that no longer replays is a bug and gives `PuzzleDataError` (500).
- The account guess (`_submit_account_guess`) ignores `previous` completely (AC-41). It loads the title, then `lock_progress` (`app/crud/progress.py`) runs `SELECT ... FOR UPDATE`; only when there is no row and the title is known, `create_progress` runs `INSERT ... ON CONFLICT (user_id, puzzle_id) DO NOTHING` and selects again (an unknown title on a first guess is refused before any INSERT, because a game with no row cannot be finished). `get_progress` and the locked read share one `_progress_query`. Then it builds the state from the stored guesses, applies the guess, stores it, builds the view and commits (the view comes before the commit, so a puzzle that cannot be shown stores nothing). The lock lasts until the commit, so two requests for one game run one after the other (AC-45), and the second reads what the first committed. Checks in order: finished (409, decided from the rebuilt state and never from the `status` column), unknown title (422), duplicate (422). The unit is `_locked_unit(db, operation=...)`, shared with the merge (see "Guest merge"). Any error from the lock to the commit calls `db.rollback()` before the original error is re-raised (a failing rollback is logged and never replaces it), so a refused guess stores nothing and leaves neither the lock nor a new empty game. The lock wait is limited by `LOCK_TIMEOUT_MS` (5 s, set with `set_local(db, "lock_timeout", ...)` from `app/core/db.py`, the one helper for transaction-local settings; the title search uses it too). Postgres error 55P03 (lock timeout) or 40P01 (deadlock), `is_lock_failure`, anywhere in that unit, in the lock, the guess insert or the commit, is 503 `service_unavailable`: nothing was stored and a retry is safe (documented on the guess route). After a rollback the session's ORM objects are expired, so nothing reads them again in the request.
- `finished_at` is the request's `now`, never earlier than `started_at`. `counts_for_streak` and `started_at` are written by the insert only, from the request's `now` (taken when the request started, so a request that waited on the lock keeps its start time): today's UTC date equal to the puzzle's date at the first guess (AC-36). `progress.puzzle_id` and `progress_guesses.title_id` are indexed. Nothing updates it. The view returns the stored value on every request. `is_test` has a database default and no code sets or returns it (AC-43).
- Views (today, dated) and resume read the stored game when there is one and create nothing; a row exists only after a guess. Resume (`games_resume_puzzle`, `private, no-store`) takes `{previous}` (capped at 20 by the schema). For an account `previous` is ignored. For a guest it is replayed with at most 6 entries (a whole lost game); an unknown title, a duplicate or an entry after the end is `invalid_guess_history`, and a replay that ended the game returns the finished view. Resume changes nothing and `counts_for_streak` is `null` for a guest.
- Tests: `tests/test_progress.py` has the tables (guest versus account, forged `previous`, error order, the flag at midnight, reads, resume, constraints) at the service and database level, and one `client` happy path for resume. The concurrency tests (AC-45) commit for real on independent sessions through the `committed` fixture, which truncates the game tables and `users` in `finally`, so run the full suite after changing them.

Title search (M1-11): `GET /v1/games/{slug}/titles?q=` (`games_search_titles`, `public, max-age=300`) returns `{"items": [{id, name, franchise, year}]}`, at most 200, with no marker for answers. The service checks the game first (`game_not_found`), then asks `search_query` (`app/games/service.py`, the one place for the rule) for the normalized text: `None` for a trimmed `q` under 2 characters or one whose normalized text is under 2 characters ("a.", "a-" and a decomposed "é" become one letter and would match up to 200 titles; "zl" is searchable), which gives an empty list; `q` over 100 characters is 422 `too_long` (`Query(max_length=100)`). The query is `search_titles` in `app/crud/title.py`: it sets `pg_trgm.word_similarity_threshold` to 0.4 for the transaction (`set_local` in `app/core/db.py`; the default 0.6 misses "zlda"), matches the normalized name or franchise with the `%>` operator (served by the GIN indexes), and orders by exact name, then `starts_with`, then the higher word similarity, then the name with `COLLATE "C"` (code point order, so ties and the cut at 200 are the same whatever the database's default collation is) and the id. The operators and `starts_with` take no wildcards and `normalize_text` removes `%`, `_` and backslashes, so `q` is always plain text (AC-22). Latency (AC-24) is checked by hand, not in CI: `ENVIRONMENT=local uv run python scripts/bench_title_search.py [--titles N]` adds 50,000 synthetic titles to the dev database (every one with the year 9999, a generated-shape name and the video game kind: its marker, so a real title with a placeholder year 9999 is never deleted), runs `VACUUM ANALYZE`, times about 200 searches on a warmed connection (the timed window holds the `set_config` too, not the pool checkout), prints the p95 (target under 150 ms), then deletes the marked rows and vacuums again. The result is printed before the cleanup, and a failed cleanup is reported with exit code 1 instead of hiding it. It also deletes marked rows at the start, so a killed run (SIGTERM, `kill -9`) is cleaned up by the next one. Without the vacuum the GIN pending lists make every search slower.

Stats and streak (M1-14): `GET /v1/games/{slug}/stats` (`games_get_stats`, `private, no-store`) takes `CurrentUser`, so a guest gets 401 `not_authenticated` (AC-46), and an optional `variant`. It checks the game, then the variant (`game_not_found`, `variant_not_found`), and returns `{played, wins, current_streak, max_streak, distribution}`.
- The rules are two pure functions in `app/games/stats.py`: `compute_stats(plays, *, today, max_guesses, variant, default_variant)` and `streaks(days, *, today)`. They take plain `Play` data (variant, puzzle date, status, guesses used, `counts_for_streak`) and no database, clock or session, so the merge test (AC-61) can call them. Every play passed to `compute_stats` must be of `variant` (finished or not), else `ValueError`; the streak fields are `null` unless `variant` is `default_variant`. `played` counts won and lost plays, archive included; `distribution` has every key from 1 to `max_guesses`; a streak day is the puzzle's date of a finished play with `counts_for_streak` true (AC-49); a gap of 1 to 3 missed days keeps the run and a gap of 4 or more starts a new one; the current streak is the last run while at most 3 days were missed since the last streak day, today not counted (AC-50).
- `list_finished_plays` (`app/crud/progress.py`) reads the account's finished rows (`status` won or lost; the stored `status` decides "finished" here) of one game and variant in one query, as plain `PlayRow`s built by column name (every select column is labelled with its field; the service turns them into `Play`s) (the query layer does not import `app/games/stats.py`). `is_test` rows are left out (AC-48), and so are rows of a puzzle that is no longer visible (`visible_puzzle_condition(today)`, as in the archive: a puzzle moved back to draft, or before a moved launch date, stops counting). The number of stored guesses is a subquery on those finished rows only.
- A win with no guesses, or with more than `max_guesses`, is bad stored data. It still counts in `played`, in `wins` and as a streak day, like any other win, and is left out of `distribution` only. `compute_stats` returns such wins in `Stats.unbucketed_wins` (it never raises), and the service logs each at warning level (not error: it repeats on every read) with the progress id, user id and puzzle date.
- For a variant other than the game's default, `current_streak` and `max_streak` are `null` (AC-51). The game guesser has no other variant yet (R-4), so the route cannot reach this today; the service test uses a module that has one.
- Computed on every read from the stored rows. No streak counter is stored (AC-53), so the stats need no migration.
- Tests: `tests/test_stats_rules.py` has the S1 to S19 and T1 to T4 tables of SPEC-02 over the pure functions, with the spec's ids as test ids; `tests/test_stats.py` has the route happy path, the guest 401, and the service tables (unknown game or variant, an `is_test` row, a game in progress, a puzzle no longer visible, the other variant).

Archive (M1-16): `GET /v1/games/{slug}/archive?variant=&before=&limit=` (`games_list_archive`, `private, no-store`) lists the visible past puzzles, newest first, as `{"items": [{date, number, state, guesses_used}], "next_before"}`. `list_archive` in `app/games/service.py` checks the game, then the variant (no `puzzle_not_found`: a missing day is just absent).
- `before` is `StrictDate`, defaults to today and is clamped to it in the service (`min(before, today)`); the query takes `date < before`, so today and the future never appear. `visible_puzzle_condition(today)` is applied too, as the second guard and for status, launch date and enabled game. `limit` is `Query(ge=1, le=100)`, default 30, read as plain digits only (`WHOLE_NUMBER` in `app/games/schemas.py`, placed after `Query` so the schema keeps `minimum` and `maximum`: `1_0`, `+5`, ` 7 `, `100.0` and `1e2` are `invalid_type`; a leading minus is allowed so `-1` is `too_small`).
- Paging is keyset on the date (unique per game and variant): `list_archive_puzzles` (`app/crud/puzzle.py`) reads `limit + 1` rows; an extra row means there is a next page, and `next_before` is then the last kept item's date, else `null`.
- A guest gets `state` and `guesses_used` as `null`. `ArchiveState` is the `ProgressStatus` values plus `not_played`; a test keeps the two in step. An account gets the stored `progress.status` (`not_played` when it has no row) and the number of stored guesses, skips included (`0` when never started), from one `LEFT JOIN` on `progress` for that user and a count subquery; nothing else of the progress leaves the query. A guest's query reads the dates only, and the service decides the nulls. `number` is the view's number.
- A past puzzle is played through the normal view, resume and guess routes (AC-66); `counts_for_streak` is `false` for it because the day is not today. A `limit` outside 1 to 100 is `too_small` (`params: {min: 1}`) or `too_large` (`params: {max: 100}`), a `limit` that is not a number is `invalid_type`, and a bad `before` is `invalid_value`.
- Tests: `tests/test_archive.py` (one route happy path for a signed-in account, one validation table, and service-level tables for paging, the clamp, visibility and gaps, ordering, the guest's nulls and the per-account state).

Guest merge (M1-15): `POST /v1/games/{slug}/progress/merge` (`games_merge_progress`, `private, no-store`) takes `CurrentUser` (a guest gets 401 `not_authenticated`) and `{entries: [{date, variant, guesses, played_as_daily, daily_proof}]}` (`daily_proof` is optional), and answers 200 with `{stored, already_present, rejected, daily_unproven, rejected_entries: [{date, variant, code}]}`. It is how a guest's local games move into the account when it signs in; it is safe to send again and to send in chunks.
- `entries` has at most 500 items (`MAX_MERGE_ENTRIES`), else 422 `too_long` with `params: {"max": 500}` and nothing is stored (AC-62). Each entry's `guesses` is capped at 20 by the schema, a size guard that gives `validation_error`; the game rule (1 to `max_guesses` guesses) is applied by the service. The body has no outcome field, and any extra field a client adds is ignored (AC-56). `variant` is capped at 32 characters, the length of `puzzles.variant`, so the rejected list cannot grow without bound.
- Daily proof (`app/games/daily_proof.py`, pure; Q2 and the owner's decision of the M1-15 review). `played_as_daily` alone is not trusted: a client could claim a streak it never played. Every view a guest gets (the view, today's view, guess and resume) carries `daily_proof`, non-null only when the server's UTC date equals the puzzle's date; an account's views always carry `null`. The proof is `base64url(HMAC-SHA256(key, "<slug>:<variant>:<YYYY-MM-DD>"))` without padding, where `key = HMAC-SHA256(SECRET_KEY, b"daily-proof-v1")` (no new setting, and not `MEDIA_SIGNING_KEY`); it has no expiry, and `verify` compares with `hmac.compare_digest`. The service sets it (`_view` in `app/games/service.py`, a validated assignment) on a view every game's view inherits from, `GameViewBase` (`app/games/schemas.py`): `daily_proof` defaults to null there and stays required in the OpenAPI response schema, so a module cannot forget it and does not set it. The derived key is cached per `SECRET_KEY` value (`functools.cache` on `_derive_key(secret)`), so a changed secret derives another key. `signed_in` stays set by the module, which gets `is_signed_in`. A merge entry's `counts_for_streak` is `played_as_daily AND verify(daily_proof, slug, variant, date)`. A claim with no valid proof is not rejected: the game is stored as an archive play (`counts_for_streak` false) and counted in `daily_unproven`, which is a count of stored entries and is not part of `stored + already_present + rejected`.
- `merge_progress` checks the game first (`game_not_found` for the whole request). The checks of one entry, in order: the guess count (1 to `max_guesses`, else `invalid_guess_history`) and the variant (`variant_not_found`), both before the database is asked anything; the visible puzzle (`puzzle_not_found`); whether the account already has a game on it, and then the entry is `already_present` at once and is never replayed, valid or not (otherwise a replay would answer "is this the answer?" with no guess used, AC-58); then the replay of the guesses through `_replay_previous` (the module's own `submit_guess`), which rejects an unknown title, a duplicate (by id or normalized name) or an entry after the end with `invalid_guess_history` (AC-39). An entry that fails the replay is checked once more, in one query before anything is stored: if the account now owns its puzzle (a game begun after the first owned read, in another tab) it is `already_present`, not rejected. The status is whatever the replay gives, finished or still in progress; a rejected entry is reported in `rejected_entries` in request order with its `date`, `variant` and code (`MergeRejectionCode`) and the others still merge (AC-59). The puzzles are loaded in one query (`list_visible_puzzles`, `app/crud/puzzle.py`: `(variant, date)` pairs under `visible_puzzle_condition`, with the answer title only, no clues or media), the account's games on them in one (`list_owned_puzzle_ids`), and the titles of the entries to replay in one.
- The write is `insert_merged_progress` (`app/crud/progress.py`): `INSERT ... ON CONFLICT (user_id, puzzle_id) DO NOTHING RETURNING id`, then the guesses in one insert. `origin` is `merge`, `started_at` is the request's `now` and so is `finished_at` of a finished game (R-23; the streak uses the puzzle's date, AC-49). A conflict means the account already has a game on the puzzle (a game begun in the meantime, or an earlier entry of the same request, where the first one wins): the row is not touched and the entry counts as `already_present` (AC-58). That is also what makes a second identical request change nothing (AC-61). The entries are stored sorted by `(variant, date)` whatever the request's order, so two overlapping merges take their row locks in the same order and cannot deadlock.
- `_locked_unit(db, operation=...)` (`app/games/service.py`) is the one unit of work for code that takes row locks and writes, used by the account guess and the merge. It limits the lock wait once per unit (`limit_lock_wait`, the 5 s `lock_timeout`; `lock_progress` no longer does, so a test that calls it directly sets the limit itself), commits when the block ends, and on any error rolls back and re-raises that error (a failing rollback is logged with the operation's name and never replaces it). A lock timeout (55P03) or a deadlock (40P01), `is_lock_failure` in `app/core/db.py`, is 503 `service_unavailable` with nothing stored, and the same request can be sent again.
- Cost: one query for the puzzles, one for the owned games, one for the titles, then one or two inserts per stored entry.
- Tests: `tests/test_merge.py`: the replay table (every status and every rejection), the unreachable puzzle and variant table, the stored fields table, the proof table (valid, none, another date, variant, game, garbage), the proof on the views of a guest and an account, the owned-puzzle oracle table, the count-first check, the insert order, one request with every kind of entry, the account's own game that wins, the second identical request (rows and stats equal, and equal to `compute_stats` over the guest's plays), a database error or deadlock stores nothing, the rollback log, and through the client the happy path (the proof comes from a guest view), the validation table (501 entries, 500 entries, bad shapes) and the guest 401.

IGDB client (M1-20): the content scripts read IGDB through `app/content/igdb.py`; the server never imports `app/content/`, so the API and the OpenAPI snapshot are unchanged. Everything about it is tested over `httpx.MockTransport` and the hand-made fixtures in `tests/fixtures/igdb/` (README there), with no network.

Never commit, print or log them or the Twitch token. The token request sends the secret in the form body, not the URL, because httpx logs URLs. The module imports `PROJECT_ROOT` from `app/core/config.py`, which builds the app `Settings` on import, so a script run needs the app's own required settings (`DATABASE_URL`, `SECRET_KEY`) in `.env` too.
- Dependencies: `[tool.uv] default-groups = ["dev", "content"]`, so `uv sync` installs both. `--no-dev` leaves `content` installed, so CI's migrations and openapi jobs (`uv sync --locked --no-dev`) also get `httpx`. Lock with CI's uv: `uvx uv@0.13.6 lock`.
- `app/content/fetch.py`: the one HTTP client factory. A request event hook refuses any host outside `api.igdb.com`, `id.twitch.tv` and `images.igdb.com`, and any non-https URL, before the request leaves; redirects are not followed; `send_capped` reads a body up to a size cap. Use it for every fetch by URL in the scripts (AC-85).
- `IgdbClient`: the token is kept in memory and read after a request has its slot; it is renewed once per query when IGDB answers 401 (a second 401 is `IgdbAuthError`). At most 4 request starts a second (`RequestSpacer`, an injected clock and sleep) and 8 open requests. Every request, the Twitch token request included, goes through one bounded retry (`_retrying`): 429, 5xx and any `httpx.RequestError` (a timeout, a refused connection, a corrupt gzip body) are retried at most 5 times (waits 1, 2, 4, 8, 16 s, or `Retry-After`, never over 60 s), then `IgdbUnavailable`. `IgdbAuthError` means Twitch answered 4xx to the token request (the credentials are wrong). `iter_pages` pages by keyset (`where id > <last>; sort id asc; limit 500`) and refuses a caller's `where` that holds `;`, sort, limit, offset or fields (`InvalidWhereError`). `games(now=...)` takes the time from the caller, for the "next year" bound of the release year.
- Validation: records are strict pydantic models. A record whose own fields are wrong is skipped and counted in `IgdbClient.skipped` by `SkipReason` (wrong shape, name with no letter or digit, year outside 1950 to next year). An invalid item inside a kept record (a genre with no name, a bad screenshot, a company given as a number) is dropped, the game is kept, and the drop is counted in `IgdbClient.dropped` by `DropReason`; a null list is empty. The two counters are kept apart so a report does not mix them, and neither holds a zero count.
- `scripts/igdb_list.py --limit 5` prints five games with every field or "missing" (AC-9). It is the check to run once the owner has credentials (gate G1): put the two keys in `.env`, run it, and compare one real record with `tests/fixtures/igdb/games_page_1.json`. It exits 1 with a message on a missing setting, a refused `--where` or any IGDB or httpx error.

- Rules: franchise is IGDB's main franchise, else the first series by IGDB id, trimmed, spaces collapsed, a trailing "(series)" style qualifier dropped, then `FRANCHISE_OVERRIDES` (`app/content/franchise_overrides.py`, keyed by source and IGDB id, empty). The year is the UTC year of the first release date. A stored title is matched by `igdb_id`; no change means no write. Nothing is ever deleted; a title that IGDB stops sending stays.
- One title for each normalized name and year (`plan_keys`). AC-14 says what to do when two IGDB games compete (the one with more ratings wins, then the lower IGDB id); the plan's M1-21 step 3 says a stored title is never replaced. Together: a stored title that keeps the key, or takes it by a rename, wins over every new game, however many ratings it has. The stored title must really hold the key at the end of the plan. A title that AC-18 refuses stays on its old key and does not hold the new one, and neither does a rename that was blocked, so that key is free: the best of the other records takes it (a stored title that wants it first, else the new game with the most ratings). Example: stored A 'Foo' has a stored guess, IGDB renames it 'Bar' and a new game 'Bar' arrives; A stays 'Foo' and the new game is added. Where a stored title outside the run (a hand-made one included), a refused title, a blocked rename or a kept title holds the key, a new game is not added and a rename onto it is not made; both count as near-duplicates. A title that is renamed away frees its old name, so a chain or a swap goes through. A blocked rename is not the end of the title: it still writes the parts that do not collide (the franchise, and a display change of the name with the same normalized name); the name and the year stay. A title refused under AC-18 stays wholly unchanged. The near-duplicate line counts records left out, so it repeats on every run while the cause stays, but the second run adds and updates nothing.

A change of the display text with the same normalized text is allowed, and so is a new year.

A franchise that is too long for its column (raw or normalized) or empty after cleaning is passed over for the next candidate.

Clue media (M1-18). Each earned step of the view has `media`: `type` (`image` or `video`), `width`, `height`, `expires_at`, `sources` (`{url, content_type}`, WebM first when there is one and MP4 last) and `poster` (`{url, content_type, expires_at}` for a video, `null` for an image). - Settings (`.env.example`): `MEDIA_STORAGE` (`local` or `s3`), `MEDIA_LOCAL_DIR` (default `var/media`, in `.gitignore`; a relative value is read from the backend repo root, `settings.media_local_path`, never from the working directory, so the seed and the server share one folder), `MEDIA_LOCAL_BASE_URL` (default `http://localhost:5173/api`, so a link loads from the frontend page through the Vite proxy with no CORS and no cookie; it may carry a plain path prefix like `/api` and nothing else: a valid host (a name, an IPv4 or a bracketed IPv6 address), no whitespace, query, fragment, credentials, `..` or escapes, `is_clean_base_url`), `MEDIA_SIGNING_KEY` (separate from `SECRET_KEY`), `MEDIA_IMAGE_LINK_TTL_SECONDS` (600, allowed 60 to 3600; images and posters) and `MEDIA_VIDEO_LINK_TTL_SECONDS` (3600, allowed 600 to 86400; a browser keeps asking for parts of a looping clip, and each request is checked), `S3_ENDPOINT_URL`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`. `s3` refuses to start with any S3 value missing; `staging` and `production` also refuse a non-https `S3_ENDPOINT_URL` (the https checks ignore the letter case of the scheme; in every environment the endpoint must be an absolute http(s) URL with no query, fragment or credentials), and with `local` a placeholder or short `MEDIA_SIGNING_KEY` (the same `is_weak_secret` rule as `SECRET_KEY`), a `MEDIA_SIGNING_KEY` equal to `SECRET_KEY`, and a non-https `MEDIA_LOCAL_BASE_URL` (the AC-72c fallback can make `local` real in production).
- A local link is `{MEDIA_LOCAL_BASE_URL}/v1/media/{key}?exp=<unix seconds>&sig=<signature>`. The signature is HMAC-SHA256 over `key:exp`, unpadded base64url, compared with `hmac.compare_digest` (`app/media/signing.py`). The key is the file's SHA-256 (AC-74), and the route accepts only `[a-f0-9]{64}`, so the file path is never built from anything else. The S3 link is a boto3 SigV4 presigned GET with `ResponseCacheControl=private` and `ResponseExpires` set to the link's own expiry (a `max-age` counts from the moment the bucket answers, so it could outlive the link), virtual-hosted addressing (the bucket in the host, as Hetzner Object Storage supports); presigning does no network call, so it runs inside async code. boto3 is imported only when the S3 storage is created, so an app with `MEDIA_STORAGE=local` never loads it. The storage is built once (`build_media_storage`, cached), at startup in the lifespan, and the `get_media_storage` dependency is `async def`, so it never runs in the threadpool; the S3 client has a `boto3.session.Session()` of its own, not boto3's shared default session.
- The route (`app/media/router.py`, `GET` and `HEAD`, outside the OpenAPI document: `include_in_schema=False`) checks in this order: the key shape, the signature and the expiry (one `403 invalid_media_link` for all three, so nothing is revealed), the visibility of the puzzle the file belongs to (`404 puzzle_not_found`, through `visible_puzzle_condition` in `get_visible_media_file`), then `Range`. The route's session dependency has `scope="function"` (`FunctionScopedSessionDep`), so the session is closed, and its connection returned to the pool, when the route function returns and before the body streams; a long clip never holds a connection. It serves the file with Starlette's `FileResponse`, the content type stored in `clue_media_files` (never guessed), `X-Content-Type-Options: nosniff` and `Cache-Control: private, max-age=<seconds the link has left>`. Its 403, 404 and 416 carry `nosniff` too (see below). With `MEDIA_STORAGE=s3` the route answers 403 to everything.
- `Range` (`app/media/ranges.py`): one valid range is served by `FileResponse` (206, `Content-Range`); a malformed or unsatisfiable one is our own `416 range_not_satisfiable` with `Content-Range: bytes */<size>` and a problem body (Starlette's own would be a plain-text 400 or 416); several ranges get the whole file with 200 (`WholeFileResponse`), not `multipart/byteranges`; a range unit other than `bytes` is ignored (the whole file, RFC 9110 section 14.2), and empty list elements (`bytes=0-1,`, `bytes=,0-1`) are skipped (section 5.6.1). The signature and expiry are checked before `Range`, on every request.
- Every `application/problem+json` response has `X-Content-Type-Options: nosniff`, set once in `problem_response` (`app/core/errors.py`), so every error of every route has it, the global 500 included; the media route has no error handling of its own. The 416 is `RangeNotSatisfiableError(size)`, and its own handler (`range_not_satisfiable_handler`) adds `Content-Range: bytes */<size>`.
- AC-72c (manual, needs a real bucket): `MEDIA_STORAGE=s3 ... uv run python scripts/check_s3_range.py` uploads the seed clip, checks that the presigned link answers `bytes=0-1` and `bytes=100-` with 206 and the right `Content-Range`, prints the link for a `<video>` check in Chrome and Safari, and deletes the object. Not run in CI. If a bucket fails it, production uses `MEDIA_STORAGE=local`. An S3 presigned link cannot add `X-Content-Type-Options: nosniff`: set the stored content type on upload and the header on the bucket if it supports it.
- Tests: `tests/test_media_signing.py` (signature, expiry, constant-time compare, key shape, both lifetimes, the S3 presign with the network blocked), `tests/test_media.py` (the `Range` table, the link checks and visibility at the service level, the route's happy path and one table of ranges and refusals, with the files in `tmp_path`), `tests/test_games.py` (the view's media, only earned steps signed, the AC-13b table, the step-1 body free of later keys) and `tests/test_seed_media.py` (the files against the manifest and the AC-74b limits, each dimension on its own). The `client` fixture overrides `get_media_storage` with `make_local_storage(tmp_path)` (a fixed key, base URL and lifetimes, never the developer's `.env`), so the view tests expect `TEST_MEDIA_BASE_URL` and `IMAGE_TTL_SECONDS`. `make_clue`, `fake_sign`, `make_local_storage` and `media_key` are in `tests/factories.py`; `create_puzzle` adds media files unless `with_media=False`.

Directory naming (`app/`, `app/api/`, `app/core/`) borrows from the [full-stack-fastapi-template](https://github.com/fastapi/full-stack-fastapi-template), but that template is flat (single `models.py`/`crud.py`, no service layer) — this project keeps the layering above instead.

## Key architectural decisions
- **Auth**: Django-style server-side sessions, not JWT. On register/login the server creates a Redis key (`session:{opaque token}` → user id, TTL = `SESSION_EXPIRE_MINUTES`) and sets it as a single httpOnly, `SameSite=Lax` session cookie (`session_id`); no access/refresh split. Logout deletes the Redis key and clears the cookie. CSRF protection (M1-41, `app/core/csrf.py`, a pure ASGI middleware that runs before routing, dependencies and body parsing): every request except GET, HEAD and OPTIONS (in practice POST, PUT, PATCH and DELETE) must send an allowed `Origin`, or, if `Origin` is absent, a `Referer` with an allowed origin; otherwise the answer is 403 `csrf_origin_mismatch`, before the session, the body or the route's own rules. GET, HEAD and OPTIONS are not checked. A POST, PUT or PATCH that carries a body must send `Content-Type: application/json` (a charset is fine), otherwise 415 `unsupported_media_type`; a body is any request with `Transfer-Encoding` (whatever `Content-Length` says), a non-zero or unreadable `Content-Length`, so an empty chunked POST without `application/json` gets 415, while a request with no body framing (for example logout from a browser) is never refused for its content type. `SameSite=Lax` stays as defense in depth. There is no custom request header (decision Q18). Allowed origins (`Settings.allowed_origins`, compared as exact scheme, host and port; no wildcard, no suffix match): the origin of `FRONTEND_URL` everywhere; in `local` and `test` also `BACKEND_CORS_ORIGINS` and `API_BASE_URL` (default `http://localhost:8000`, so "Try it out" on `/docs` works). uvicorn prints `http://127.0.0.1:8000`, but open `/docs` at `http://localhost:8000` for "Try it out": `127.0.0.1` is not an allowed origin. With curl or a script, add `-H 'Origin: http://localhost:5173'` (and `-H 'Content-Type: application/json'` when sending a body). Tests: the `client` fixture sends `Origin: http://localhost:5173` by default. Every `application/problem+json` error response of the API, auth included, carries `Cache-Control: no-store`; CORSMiddleware's own plain-text 400 on a refused preflight (dev only) is not one of them. This API is always the source of truth for validation — the frontend's client-side checks are a UX convenience only, never trusted as-is. Dev note: the session cookie is host-scoped, so the frontend must reach the backend via `http://localhost:8000` (not `127.0.0.1:8000`) for the cookie to round-trip from `http://localhost:5173`.
- **CORS**: only for local development, where Vite runs on another port (`BACKEND_CORS_ORIGINS`, default `http://localhost:5173`). Production is same origin behind the proxy, so it needs no CORS, and `staging` and `production` refuse to start with localhost origins (`app/main.py`, `app/core/config.py`).

## Conventions
- Run everything through `uv run ...` (or `.venv/bin/...`); `uv.lock` is the source of truth for pinned versions
- Async all the way through DB access; sync only for genuinely CPU-bound or blocking code
- Tests: pytest + pytest-asyncio + httpx `ASGITransport`
- Lint/format: ruff
